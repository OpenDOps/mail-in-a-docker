# Mail-in-a-Box Helm Chart

This Helm chart deploys Mail-in-a-Box on Kubernetes, replacing the nginx container with Kubernetes Ingress and using cert-manager for TLS certificate management.

## Prerequisites

- Kubernetes 1.19+
- Helm 3.0+
- nginx-ingress controller installed
- cert-manager installed (optional, for automatic TLS certificates)

## Installation

### 1. Install cert-manager (if not already installed)

```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.13.0/cert-manager.yaml
```

### 2. Create a ClusterIssuer for Let's Encrypt

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: your-email@example.com
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
    - http01:
        ingress:
          class: nginx
```

### 3. Install the chart

```bash
helm install mailinabox ./helm/mailinabox
```

## Configuration

The following table lists the configurable parameters and their default values:

| Parameter | Description | Default |
|-----------|-------------|---------|
| `mailinabox.env.primaryHostname` | Primary hostname for the mail server | `box.example.com` |
| `mailinabox.env.publicIP` | Public IP address (leave empty to auto-detect) | `""` |
| `mailinabox.storage.size` | Size of mail storage PVC | `50Gi` |
| `ingress.enabled` | Enable ingress | `true` |
| `ingress.className` | Ingress class name | `nginx` |
| `certManager.enabled` | Enable cert-manager integration | `true` |
| `certManager.clusterIssuer` | Cert-manager ClusterIssuer name | `letsencrypt-prod` |
| `nsd.enabled` | Enable NSD authoritative DNS | `true` |
| `bind.enabled` | Enable BIND recursive resolver | `false` |

## Key Differences from Docker Compose

1. **No nginx container**: Replaced with Kubernetes Ingress using nginx-ingress controller
2. **Cert-manager integration**: TLS certificates are managed by cert-manager and mounted as secrets
3. **PersistentVolumes**: All volumes are converted to PersistentVolumeClaims
4. **Service discovery**: Uses Kubernetes DNS instead of Docker network IPs
5. **Certificate paths**: Mail-in-a-Box reads certificates from `/etc/ssl/certs/tls.crt` and `/etc/ssl/private/tls.key` (mounted from cert-manager secret)
6. **Nginx config generation**: **Disabled in Kubernetes mode**. The `nginx-config` PVC has been removed. Instead, Ingress resources should be generated by the mailinabox management daemon (future enhancement).

## Nginx Configuration vs Ingress Resources

**Important**: In Kubernetes, nginx config files are **NOT generated or used**. Instead:

1. **Ingress resources** are used for routing (defined in `ingress.yaml`)
2. The mailinabox management daemon should be modified to generate Ingress resources instead of nginx configs
3. When `IN_KUBERNETES=true` is set, nginx config generation is disabled

### Current Implementation

- The Helm chart sets `IN_KUBERNETES=true` environment variable
- The nginx-config PVC has been **removed** (not needed)
- A static Ingress resource is provided in `ingress.yaml` for the primary hostname

### Future Enhancement

The mailinabox management daemon should be modified to:

1. Detect `IN_KUBERNETES=true` environment variable
2. Generate Ingress resources dynamically based on configured domains
3. Use Kubernetes API to create/update Ingress resources
4. Handle SSL certificates via cert-manager annotations automatically

This would allow:

- Automatic Ingress creation for new mail domains
- Dynamic SSL certificate provisioning via cert-manager
- Proper Kubernetes-native configuration management

## Certificate Management

Certificates are automatically provisioned by cert-manager when:

- `certManager.enabled` is `true`
- A ClusterIssuer is configured
- Ingress is enabled with TLS configuration

### How Certificates Are Mounted

1. **cert-manager Certificate resource** (`certificate.yaml`) requests a certificate from the ClusterIssuer
2. **cert-manager creates a Kubernetes Secret** with keys: `tls.crt`, `tls.key`, `ca.crt`
3. **The secret is referenced in Ingress** for TLS termination at the ingress level
4. **The same secret is mounted in the mailinabox pod** as volumes:
   - Certificate: `/etc/ssl/certs/tls.crt`
   - Private key: `/etc/ssl/private/tls.key`
5. **Environment variables** (`SSL_CERTIFICATE`, `SSL_KEY`) point mailinabox services to these paths

**Key points:**

- Single source of truth: cert-manager Certificate resource
- Automatic renewal: cert-manager renews certificates before expiration
- Automatic updates: When the secret is updated, Kubernetes automatically updates mounted volumes
- Dual usage: Same secret used by both ingress controller and mailinabox services

See `CERTIFICATE_MOUNTING.md` for detailed explanation.

## Storage

All persistent volumes are created as PersistentVolumeClaims. Make sure your cluster has a default StorageClass or specify one in `values.yaml`.

## DNS Configuration

- **NSD**: Authoritative DNS server (enabled by default)
- **BIND**: Recursive resolver (disabled by default, enable if your cluster DNS doesn't support DNSSEC validation)

## Uninstallation

```bash
helm uninstall mailinabox
```

Note: This will NOT delete PersistentVolumeClaims. To remove them manually:

```bash
kubectl delete pvc -l app.kubernetes.io/instance=mailinabox
```
