# Mail-in-a-Pods

This is a dockerized mail infrastructure, adapted for docker-compose and Kubernetes. This project is based on [Mail-in-a-Box (MIAB)](https://github.com/mail-in-a-box/mailinabox), but separates components and makes it scalable and able to run in a Kubernetes cluster.

It is using light-weight Alpine-based containers.

You can install it to your cluster with `helm chart` or use a `docker compose` on a stand-alone machine.

## Mail-in-a-Box Container Layout

This repository repackages Mail-in-a-Box into multiple Docker images:

- `mailinabox`: core mail/control-plane services (Postfix, Dovecot, web UI, etc.).
- `web/nginx`: (not for Kubernetes deployment) reverse proxy and web server that handles HTTP/HTTPS traffic. Nginx configuration is dynamically generated by the mailinabox management daemon and shared via a Docker volume (`nginx_config`). The mailinabox container writes nginx configs to `/var/lib/mailinabox/nginx-config`, which is mounted read-only in the nginx container at `/etc/nginx/conf.d`. This ensures a single source of truth for nginx configuration. In a Kubernetes deployment this component is replaced by ingress.
- `dns/nsd`: authoritative DNS server responsible for publishing your domains and DNSSEC keys.
- `dns/bind`: optional recursive resolver used only when you want a local, DNSSEC-validating resolver.

`docker-compose.yml` wires the services together with shared volumes:

- `mail_storage`: shared mail data and SSL certificates
- `nginx_config`: nginx configuration generated by mailinabox (mailinabox writes, nginx reads)
- Application volumes for Roundcube, Nextcloud, Z-Push, and mailinabox assets

It is not using Munin from originlal Mail-In-A-Box, as there are more common monitoring tooling for docker and kubernetes.

## Process Management with s6-overlay

This project uses [s6-overlay](https://github.com/just-containers/s6-overlay) for process supervision and service management within containers. s6-overlay provides:

- **Process supervision**: Automatically restarts services if they crash
- **Service dependencies**: Services can depend on other services and wait for them to be ready
- **Ordered startup**: Init scripts run before services, ensuring proper initialization order
- **Graceful shutdown**: Handles SIGTERM/SIGINT signals properly for clean container shutdown
- **One-shot services**: Support for services that run once and exit (e.g., initialization tasks)

### How s6 works in our containers

1. **Init scripts** (`/etc/cont-init.d/`): Run once at container startup, before services start. Used for:
   - **Mailinabox container**: Setting up DNS resolver configuration, runtime configuration of Postfix and Dovecot, initializing storage and databases
   - **Nginx container**: Waiting for mailinabox daemon to be ready, waiting for nginx configuration from mailinabox management daemon, validating nginx configuration

2. **Mailinabox container services** (`/etc/services.d/`): Long-running processes managed by s6:
   - `mailinabox`: Management daemon (gunicorn) serving the web UI and API
   - `postfix`: Mail transfer agent
   - `dovecot`: IMAP/POP3 server
   - `opendkim`: DomainKeys Identified Mail (DKIM) signing service
   - `opendmarc`: Domain-based Message Authentication, Reporting & Conformance (DMARC) service
   - `postgrey`: Greylisting service for spam prevention
   - `cron`: Cron daemon for scheduled tasks
   - `web-update-init`: One-time service that generates nginx config after mailinabox daemon starts

3. **Nginx container services** (`/etc/services.d/`): Long-running processes managed by s6:
   - `nginx`: Web server and reverse proxy that handles HTTP/HTTPS traffic
   - `php-fpm`: PHP FastCGI Process Manager (only if `WITH_PHP=true`, used for webmail and other PHP applications)
   - `nginx-reload-watcher`: Service that monitors nginx configuration changes and automatically reloads nginx when the mailinabox management daemon updates the config

4. **Service types**:
   - **Long-running**: Services that run continuously (most services)
   - **One-shot**: Services that run once and exit (e.g., `web-update-init`). To create a one-shot service in s6-overlay:
     - The service's `run` script should call `s6-svc -d /run/service/SERVICE_NAME` before exiting to down the service and prevent restart
     - adding `down` file makes service unstartable, or if already started it is not refreshed and ignores added `down` file
     - adding `finish` with exit code `111` also doesn't stop the service

### Why s6 instead of systemd or supervisord?

- **Lightweight**: s6 is designed for containers and has minimal overhead
- **Alpine-compatible**: Works well with Alpine Linux base images (no systemd dependency)
- **Container-native**: Designed from the ground up for containerized environments
- **Reliable**: Handles process crashes, signal propagation, and service dependencies robustly

## TLS/SSL Certificates

### Automatic Placeholder Certificate Generation

The system is designed to start successfully even when SSL certificates are not yet provisioned. When the mailinabox management daemon generates nginx configuration and detects missing SSL certificates, it automatically creates **placeholder self-signed certificates**:

- **Private key**: 2048-bit RSA key generated at `/home/user-data/ssl/ssl_private_key.pem`
- **Certificate**: Self-signed certificate valid for 365 days at `/home/user-data/ssl/ssl_certificate.pem`
- **Purpose**: Allows nginx to start and serve HTTPS traffic immediately, even before real certificates are provisioned

### Certificate Lifecycle

1. **Initial startup**: If no certificates exist, placeholder self-signed certificates are automatically generated
2. **Nginx starts**: Nginx can start with the placeholder certificates (browsers will show security warnings)
3. **Certificate provisioning**: Real certificates can be provisioned later via:
   - Let's Encrypt (via the control panel or certbot)
   - Manual installation through the control panel
   - External certificate management (e.g., cert-manager in Kubernetes)
4. **Replacement**: When real certificates are installed, they automatically replace the placeholder certificates

### Important Notes

- **Self-signed certificates**: The placeholder certificates are self-signed and will trigger browser security warnings. This is expected and normal for initial setup.
- **Replacement**: Placeholder certificates are automatically replaced when real certificates are provisioned - no manual intervention needed.
- **Kubernetes**: For Kubernetes deployments, it's recommended to set `WITH_SSL=false` and handle TLS at the ingress level using cert-manager or similar tools.

### Certificate Storage

In a `docket-compose` deployment certificates are stored in the `mail_storage` volume at `/home/user-data/ssl/` and are shared between containers that need them: mailinabox (with dovecot & postfix), nginx.

In a Kubernetes deployment certificates should be managed by cert-manager and stored in a shared secret.

## Security and Version Pinning

This project implements **strict version pinning** for all dependencies to mitigate supply chain attack risks. All Docker images, system packages (Alpine `apk`), and Python packages (`pip`) use exact version specifications.

### Why Version Pinning?

Supply chain attacks occur when malicious code is introduced through dependencies. By pinning exact versions:

- **Reproducibility**: Every build uses identical dependencies
- **Predictability**: No unexpected changes from upstream updates
- **Security**: Reduced exposure to vulnerabilities in newer, untested versions
- **Auditability**: Clear record of what versions are in use

### Implementation

- **Base Images**: Pinned to specific Alpine version (`alpine:3.20`)
- **System Packages**: All `apk` packages pinned with exact versions (e.g., `bash=5.2.26-r0`)
- **Python Packages**: All `pip` packages pinned in `requirements.txt` and `requirements-system.txt`

### Updating Dependencies

When updating dependencies:

1. Check security advisories (CVE databases, security bulletins)
2. Test thoroughly in a test environment first
3. Update `requirements.txt` or Dockerfiles with new versions
4. Verify all Docker images build successfully
5. **Update [DEPENDENCIES.md](DEPENDENCIES.md)** with the new versions
6. Document changes in commit messages

For more details, see [SECURITY.md](SECURITY.md).

### Dependency Documentation

A complete list of all dependencies (Alpine `apk` packages and Python `pip` packages) with their pinned versions is maintained in [DEPENDENCIES.md](DEPENDENCIES.md). This document:

- Lists all packages used across all containers
- Groups packages by name when used in multiple containers
- Shows which containers use each package
- Includes version information for security auditing

**Important**: When adding, removing, or updating dependencies, you must update `DEPENDENCIES.md` to keep it in sync with the actual dependencies in use.

This repository uses **pre-commit** hooks (see `README-PRE-COMMIT.md` for details) to enforce consistent formatting, linting, and basic security hygiene across:

- Shell scripts (ShellCheck)
- Dockerfiles (hadolint)

#### Helm Chart Autotesting

The pre-commit hooks include automatic Helm chart testing that validates chart templates with test values files:

**How it works:**

1. **Test values files**: Place test values files in the `helmtest/` folder at the project root, named as `{chart-name}-values*.yaml` (e.g., `mail-in-a-pods-values-correct.yaml`)

2. **Automatic testing**: When you commit changes to Helm chart files, the pre-commit hook will:
   - Find all test values files matching `{chart-name}-values*.yaml` in `helmtest/`
   - Render the chart template with each test values file
   - Save the rendered output to `helmtest/results/{file-name}-result.yaml`
   - If any template rendering fails, the commit is blocked with an error message

3. **Fallback behavior**: If no test values files are found for a chart, the hook will:
   - Use the default `values.yaml` from the chart directory
   - Render the template and save to `helmtest/results/{chart-name}-values-result.yaml`

**Manual execution:**

To run Helm template tests manually (outside of pre-commit):

```bash
# Run the test script directly
./scripts/test-helm-charts.sh

# Or via pre-commit
pre-commit run helmtemplate --all-files

# Test a specific chart manually
cd helm/mail-in-a-pods
helm template helm-test . --values ../../helmtest/mail-in-a-pods-values-correct.yaml > ../../helmtest/results/mail-in-a-pods-values-correct-result.yaml
```

**Test values file structure:**

Create test values files in `helmtest/` to test different scenarios:

```yaml
# helmtest/mail-in-a-pods-values-correct.yaml
global:
  storageClass: vultr-block-storage
  nodeSelector:
    kubernetes.io/os: linux
  tolerations:
    - key: node-role
      operator: Equal
      value: system-workloads
      effect: NoExecute

mailinabox:
  storage:
    size: 50Gi
```

The rendered templates are saved to `helmtest/results/` for inspection and can be used to verify that changes to templates produce the expected Kubernetes manifests.

### CI/CD workflows: building Docker images and publishing the Helm chart

This repository uses GitHub Actions workflows to automate:

- **Docker image builds** (for `mailinabox`, `nginx`, `nsd`, `bind`) and optional variants
- **Helm chart publishing** to an OCI registry: `oci://ghcr.io/opendops/mail-in-a-pods`

The Helm publishing workflow (`.github/workflows/prepare-helm.yaml`) runs on pushes to `main`/`helm` that touch Helm files, and on manual `workflow_dispatch`. It:

- Lints the chart with `helm lint`
- Packages the chart
- Pushes it to GHCR as an OCI Helm package at `oci://ghcr.io/opendops/mail-in-a-pods`

#### Verifying that the Helm chart is published and public

To verify that the chart was published **and is publicly accessible**:

**Log out from GHCR (to simulate an anonymous user):**

```bash
helm registry logout ghcr.io 2>/dev/null || true
```

**Pull the chart from the OCI registry:**

```bash
helm pull oci://ghcr.io/opendops/mail-in-a-pods --version 0.1.1
```

**Inspect the chart metadata:**

```bash
helm show chart oci://ghcr.io/opendops/mail-in-a-pods --version 0.1.1
```

If these commands succeed without authentication, the chart is published and publicly readable.

If you get `401 unauthorized` or `403 denied`, ensure the GHCR package is public:

- Open the package settings in GitHub (`https://github.com/orgs/OpenDOps/packages/container/mail-in-a-pods/settings`)
- Set the **Package visibility** to **Public** and save

#### Configuration via .env file

All default configuration values are defined in the `.env` file, which serves as the **single source of truth** for your MailInABox setup. This approach provides:

- **Centralized configuration**: All defaults are defined in one place (`.env` file)
- **Easy customization**: Edit `.env` without modifying `docker-compose.yml`
- **Version control friendly**: Add `.env` to `.gitignore` and commit `.env.example` if needed
- **Works with both build args and environment variables**: Docker Compose automatically loads variables from `.env`

The `.env` file contains all configurable variables including:

- `WITH_PHP`: Do we install PHP FPM in nginx (default: `true`)
- `PHP_VER`: PHP version (default: `8.2`)
- `PRIMARY_HOSTNAME`: Primary hostname (default: `box.example.com`)
- `STORAGE_ROOT`: Storage root path (default: `/home/user-data`)
- `STORAGE_USER`: Storage user (default: `user-data`)
- `PUBLIC_IP`: Public IP address
- `MAILINABOX_VERSION`: MailInABox version (default: `v73`)
- `WITH_SSL`: Enable SSL and certbot inside a mailinabox container (default: `true`)
- `INSTALL_FAIL2BAN`: Install fail2ban (default: `false`)
- `ENABLE_INTERNAL_BIND`: Enable internal BIND (default: `false`)
- `DEFAULT_MTA_STS_MODE`: MTA-STS mode (default: `enforce`)

To customize your setup, simply edit the `.env` file with your desired values. Docker Compose will automatically use these values when building and running containers.

### Running on Kubernetes

- **Authoritative DNS (`nsd`)**: keep it. Mail-in-a-Box needs to generate and serve zone files and DNSSEC signatures locally.
- **Recursive DNS (`bind`)**: only keep it if your cluster resolver (usually CoreDNS/kube-dns) cannot provide *all* of the following:
  - DNSSEC validation for outbound lookups (required for DANE, TLSA, etc.).
  - Unfiltered access to DNSBL/RBL zones used by Mail-in-a-Box (some shared resolvers block these queries).
  - Reliable responses without aggressive rate limiting that could impact spam filtering or monitoring.

If your Kubernetes DNS is DNSSEC-capable and doesn’t block RBL traffic,
set `ENABLE_INTERNAL_BIND=false` (default) and just point the `mailinabox` container’s resolver (`LOCAL_RESOLVER`) at the cluster DNS service. If the cluster resolver can’t meet these requirements, deploy the `dns/bind` image (as a separate pod or DaemonSet) so Mail-in-a-Box has a dedicated validating resolver.

Build with `WITH_SSL=true` argument to handle certificates with cert-bot. It should be done by cert-bot, but need more configuring.
